## Refutations (detail)

### R-a: r8a-4 "`put_from` buffers the entire upload to a temp file" - not a defect

The disk-temp shape is a deliberate, documented trade-off (src/store/s3.rs:519-522 comment: "never a size-sized in-memory buffer"; object-store.md:69 states the design and the 5 GiB ceiling). The reviewer agrees: "The current approach is correct and safe for v1 - just flagging the overhead." Direct streaming from the reader requires a known-content-length `SdkBody` reshape; multipart is the real residual and is already tracked (roadmap Phase 3 item 4, reworded under W84). No code action.

### R-b: r8a-6 "`check_destination` called twice per download" - by design, not redundant IO

The two calls guard **different** windows, and the code says so (src/exec.rs:268-272, :299-303):

- Pre-check (W68): a pure earlier-fail optimization that runs **before** the potentially multi-hundred-MB body streams, so a stale destination refuses cheaply.
- Post-body check (W13/W22, N3): owns the plan-to-rename race window - a writer landing between the pre-check and the rename must still be refused.

Removing the pre-check re-introduces the "refused key still pays the whole download" cost W68 was filed to fix; removing the post-check re-opens the N3 rename window. The cost of "both always run" is two `symlink_metadata` + `metadata` stat pairs per download - noise next to the body stream they gate. r9 independently reached the same conclusion (r9-N3: "intentional and cheap relative to the body stream it gates; the docs say exactly this"). No code action.

### R-c: r8a-7 "no `Drop` impl / graceful shutdown for the tokio runtime" - informational only

`S3Store` owns a current-thread `Runtime`; `Runtime::drop` blocks until in-flight work finishes or the process dies, which is the correct Phase 2 semantic. A SIGKILL mid-`block_on` aborts an in-flight S3 request, but the temp-file discipline (upload temp removed on error paths, W29 stale-temp skip; download temp + created dirs removed, W66) means no partial local state survives. Graceful shutdown with a timeout is a Phase 3 concurrency concern, where multiple in-flight operations exist. The reviewer rates this informational. No code action.

### R-d: r8a-8 "`walk` does not limit directory depth" - already tracked

The deferral is explicit and current: roadmap.md:170 - "Walker depth (Phase 3 note): recursion is unbounded; add a depth cap or iterative walk during hardening ... RE-DEFERRED to Phase 3". The reviewer's ask was "just confirming this is tracked". Confirmed; no new action. (The symlink-cycle half is already guarded by the `visited` canonical-target set; hardlinked directories are not creatable by unprivileged users on APFS/ext4.)

### R-e: r8b-L1 cli.md portion - cli.md does not over-claim

The claim: "doc/cli.md 'Local deletes re-verify freshness' and the `delete_file_guarded` rustdoc **both** state the parent-swap half is closed." Only the rustdoc (and the seam doc) do. doc/cli.md:191-205 describes freshness re-verification, the head-before-delete remote guard, and the leaf check-then-act residual ("a leaf swapped in the window between the stat and the unlink is still removed"); it makes **no** statement about the parent-swap half in either direction (verified: no "parent"/"locality" match in cli.md). The rustdoc over-claim is real and is resolved by W76 making the documented behavior true - per the reviewer's own "do not soften the docs around the bug" - so no cli.md edit is needed.

### R-f: r9-N4 "W70 warning repeats per `list` call" - accepted as designed

`status` then `push` warning twice for a persistent `*/` object is the intended "surface, don't hide" behavior for v1; the reviewer rates dedup "a Phase 3 polish item". No action.
