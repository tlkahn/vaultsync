## Implementation discipline (strict fine-grained TDD)

- Every behavior change starts RED: the new/extended test is written first and run (`cargo test --offline --lib <name>`) to observe it failing **for the stated reason** before any implementation is touched. The `RED:` annotation stays in the landed test comment (existing house style; the review explicitly said no need to scrub).
- GREEN: minimal implementation to pass the new tests, then the full gate.
- Refactor (visibility, comment, and doc items) only under a green gate; no behavior change.
- Pure pin tests (W131) that pass on first run get a **mutation check**: temporarily break the implementation, observe the pin go RED, restore, observe GREEN - so the pin is proven to bite, not aspirational.
- Docs-only items have no RED/GREEN cycle (no behavior); each lands under the all-green gate.
- Gate per commit: `cargo fmt --check` + `cargo clippy --offline --all-targets -- -D warnings` + `cargo test --offline --lib`. Before the final push also run the full `cargo test --offline` (env-gated integration tests self-skip without credentials).
- One commit per work item (fine-grained, bisectable); the only behavior change (W130) lands alone and first.

### W130 - M2: reject zero `base_delay_ms` / `max_delay_ms` at resolution (code + tests)

TDD cycle in `src/config.rs`.

**RED (tests first).** Add to the config tests module:

1. `resolve_settings_retry_rejects_zero_base_delay` - `[transfer.retry]\nbase_delay_ms = 0` must error, message naming `transfer.retry.base_delay_ms` with a non-zero/"must be >= 1" reason. Fails today: resolves fine (0 <= 20000).
2. `resolve_settings_retry_rejects_zero_max_delay` - two sub-cases:
   - `max_delay_ms = 0` alone must error naming `transfer.retry.max_delay_ms` with the non-zero reason. Today it errors via the base>max rule (names both keys but with the wrong reason: "base must not exceed max"), so asserting the new wording is RED.
   - `base_delay_ms = 0` + `max_delay_ms = 0` together resolve today (reviewer's example); must error. (With the zero checks ordered base-first, this names `base_delay_ms`.)
3. `resolve_settings_retry_allows_equal_base_and_max` - boundary pin (reviewer: "equal base==max with both > 0 is fine"): `base_delay_ms = 500` + `max_delay_ms = 500` resolves. Passes already; kept to lock the boundary against an over-eager `<` check.

Run `cargo test --offline --lib resolve_settings_retry` and observe 1 and 2 fail for the stated reasons.

**GREEN.** In `resolve_retry` (`src/config.rs`), add the zero checks **before** the existing `base > max` check (so a lone `max_delay_ms = 0` names the right key with the right reason), mirroring the existing loud key-naming style (W56 ethos):

```rust
if base_delay_ms == 0 {
    return Err(Error::Other(format!(
        "transfer.retry.base_delay_ms must be >= 1 (the SDK requires a non-zero initial backoff), got {base_delay_ms}"
    )));
}
if max_delay_ms == 0 {
    return Err(Error::Other(format!(
        "transfer.retry.max_delay_ms must be >= 1 (the SDK requires a non-zero max backoff), got {max_delay_ms}"
    )));
}
```

The check runs on resolved values; the defaults (1000/20000) are non-zero, so resolved-checks and explicit-checks are equivalent here.

**Refactor:** none expected.

Also update the cli.md validation sentence (keep docs true with the code): "`max_attempts` must be >= 1 and `base_delay_ms` <= `max_delay_ms`" -> add "both delays must be >= 1 (the SDK requires non-zero backoffs)".
