## Refutations (false-positive mechanisms)

### R-a. N2/L3's "symlink planted at the destination is silently overwritten/written through" - overstated

`finalize_write` commits with `std::fs::rename(tmp, &path)`. `rename(2)` atomically replaces the directory *entry* at `path`; it never follows or writes through a symlink sitting there. A symlink planted at the destination after planning is **replaced** by the rename (the link is destroyed, its target untouched) - no out-of-vault write occurs. This matches the existing lock `exec_download_destination_symlink_fails_closed`, which passes precisely because the guard fires before rename, but even without the guard the write-through scenario cannot happen on the rename path.

What **is** real in N2/L3: a *regular file* created at the destination between plan and execute (editor save, another tool) is silently clobbered by the rename, because the freshness guard only runs when the plan recorded a local entity. The fix (W22) is still warranted on the data-clobber ground alone; the symlink framing should not be cited as additional urgency.

### R-b. L1's "open write handle blocks a second open on Windows" - refuted mechanism, hygiene kept

Rust `std` opens files on Windows with `FILE_SHARE_READ | FILE_SHARE_WRITE | FILE_SHARE_DELETE` by default (`OpenOptions` only narrows this if `.share_mode()` is called, which vaultsync never does - verified by grep). A `File` still open for write therefore does **not** block the subsequent `ByteStream::from_path` read open; the described Windows breakage cannot occur in this codebase. The explicit `drop(f)` before `from_path` is kept (W30) purely as zero-cost hygiene / intent documentation, not as a bug fix. Severity: none.
