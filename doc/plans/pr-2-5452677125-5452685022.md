## Refutations (detail)

### R-a: B nit "case-collision reason dropped by the followed-symlink override" - false positive

The two overrides in `build_plan` are ordered and disjoint on `kind`:

1. Case-collision preflight (src/lib.rs:66-77): for collided keys, sets `a.kind = Conflict; a.reason = CASE_COLLISION` (skipping only rows already diagnosed `PATH_COLLISION`).
2. Followed-symlink override (src/lib.rs:90-99): rewrites only `Upload | Download | DeleteLocal` rows to `Skip(followed_symlink)`.

After step 1 a both-conditions key is `Conflict`, and `Conflict` is not matched by step 2's `matches!`, so the `case_collision` Conflict survives in mutating modes. The claimed reason-drop cannot occur. W72 locks this with a characterization test so a future refactor that reorders or widens the overrides fails loudly.

### R-b: A-L5 dedup (as opposed to warning) - declined

Recording canonical paths of real directories in `visited` (the reviewer's first option) would make the surviving key set depend on `read_dir` enumeration order: if `linkdir` is visited before `realdir`, the real dir would be the one skipped; if after, the link. A sync tool must not have a nondeterministic inventory. The deterministic half of the ask - "at least warning on the alias" - is W67.

### R-c: A-M2 mtime comparison - deviated to size-only

The reviewer's spec ("comparing size + mtime within the plan tolerance against the planned entity") mixes mtime sources: the planned remote entity's `mtime_ms` is the listing's `LastModified`, while `head` prefers the `vaultsync-mtime` client metadata (src/store/s3.rs:357-359, decode order in `decode_mtime`). For any object whose client mtime differs from its upload time by more than the tolerance - the common case, and the entire reason the list-skew limitation is documented - the comparison would false-fail the delete. W62 therefore compares **size** (same source on both sides: object Content-Length) and documents the same-size-replacement residual alongside the existing N3 residuals.
