## Part 1: Full-diff review comment (5454418745) - verdicts

### H1 `eprintln!` warnings in library code - CONFIRMED, fix (W99)

Verified at src/store/s3.rs:469 (`S3Store::list` warns per dropped non-empty
trailing-`/` key) and src/lib.rs:65 (`build_plan` warns on reserved-namespace
remote keys). Both are library-code writes to the process stderr that a
non-CLI consumer cannot capture or suppress, and both are inconsistent with
the executor's own `ExecReport.warnings` channel (src/exec.rs:29-31). Real
design debt for the Phase 3 `--json` output contract. Fix: thread a
structured warning channel through `ObjectStore::list` and `build_plan`
(design under W99 below) and print from the CLI dispatch layer only.

### H2 `reap_stale_upload_temps` runs on every `S3Store::new()` - CONFIRMED, fix (W97)

Verified at src/store/s3.rs:65: the constructor unconditionally scans the OS
temp dir. The scan is one `read_dir` + per-entry metadata only on
`vaultsync-upload-*` names, so real-world cost is small (severity "High" is
overstated), but a library constructor performing a directory sweep on every
call is the wrong shape: construction should be cheap and idempotent, and
tests constructing many stores re-scan repeatedly. Fix: gate the reap behind
a process-wide `OnceLock` so it runs at most once per process (W88's
best-effort, swallow-all-errors semantics unchanged).

### H3 no backpressure or size limit on listing results - CONFIRMED as design constraint, document (W100)

Verified: `list_prefix_objects` (src/store/s3.rs:102) collects all pages into
one `Vec`; the planner collects entities into `HashMap`s. Unbounded growth is
real but acceptable for the v1 vault-scale target; the reviewer agrees
("likely fine"). No code change: document the in-memory-listing constraint in
doc/object-store.md so Phase 3 concurrency/streaming work starts from an
explicit assumption.

### M4 redundant `client.clone()` / `bucket.clone()` in every S3 operation - CONFIRMED, fix (W101)

Verified at five sites (src/store/s3.rs:107-108, 479-480, 509-510, 612-613,
640-641). `Runtime::block_on` does not require `'static` futures; the async
blocks can borrow `self.client` / `self.bucket` (keeping `async move` only
where an owned local like `fk`/`rel` is consumed, e.g. into the returned
`Entity`). The `Client` clone is an Arc bump but `bucket` is a `String` clone
per call. Behavior-neutral refactor under the all-green suite.

### M5 duplicated freshness-check logic between download and delete paths - CONFIRMED, fix (W102)

Verified: `destination_freshness` (src/local.rs:349-388) and the inline check
in `delete_file_guarded` (src/local.rs:546-562) implement the same
size-equality + mtime-within-tolerance comparison with different wrappers
(`Freshness::Changed` vs direct `Err`). A tolerance-semantics change (e.g. a
Phase 3 checksum input) would have to be made in lockstep at both sites.
Fix: extract one shared staleness predicate used by both.

### M6 `debug_assert!` in `classify_pair` silently passes folders in release builds - REFUTED

The suggested early `return` would be dead, untestable code. The caller
`resolve` (src/plan/mod.rs:271-273) returns `(Skip, reason::FOLDER)` for any
folder entity *before* `classify_pair` is reached, so the invariant is
enforced at the single call site, and the `debug_assert!` (src/plan/mod.rs:130)
exists to catch a future caller that violates it in tests/debug builds. This
matches the file's established contract-assert style (the duplicate-key
`debug_assert_eq!`s at src/plan/mod.rs:171-176 guard the same "planner input
contract" class). Replacing the assert with a silent release-mode return would
mask a planner bug instead of surfacing it. No change.

### M7 `convert_listed` intermediate allocation - CONFIRMED, fix (W103)

Verified at src/store/s3.rs:287: `map.keys().cloned().collect()` clones every
file key into a `Vec<String>` only to feed `parent_folders` (which allocates
its own `String`s anyway). Collecting parent folders directly from
`map.keys()` into one `Vec<String>` (required before mutating `map`) drops the
full key clone. Behavior-neutral refactor; the existing synthesis/dropped-key
tests guard it.

### L8 module size (local.rs 2,736 / cli.rs 1,858 lines) - DECLINED

Inline `#[cfg(test)]` modules are the established convention across the whole
tree and the entire W-series; every prior plan references tests by file:line
under that layout. Splitting now is navigability churn with no behavior or
coverage gain, and would invalidate those references. Revisit only if a file
grows a genuinely independent second concern.

### L9 comment traceability codes (W/A/B/R/N/L) add visual density - DECLINED

The codes are the active cross-referencing mechanism between review rounds,
disposition comments, and these fix plans (this document cites them). Stripping
them while review rounds are in flight would break that trail. A one-time
narrative-to-docs pass is a legitimate post-merge, pre-Phase-3 housekeeping
idea, but it is a docs decision, not a code-quality fix.

### L10 `ExecReport.executed` is `u32` - DECLINED

The bound is deliberate and sufficient (2^32 actions against any real vault),
there is no behavioral defect, and the type change ripples through the report
struct and its consumers for a cosmetic gain. Not a true quality improvement.

### L11 `fold_key` uses locale-dependent `to_lowercase()` - REFUTED

The premise is factually wrong about Rust: `str::to_lowercase` implements the
Unicode Default Case Conversion and is locale-*independent* - it applies no
Turkish dotless-i special-casing (Rust has no locale-sensitive case API; that
is a Java/Go behavior). Beyond that, Unicode-aware folding is the correct
target for `fold_key`'s purpose (detecting collisions on case-insensitive
filesystems like APFS/NTFS, which fold full Unicode); switching to
`to_ascii_lowercase()` would *weaken* collision detection for non-ASCII vault
names. No change.

### L12 integration test `with_store` cleanup does not report failures - CONFIRMED, fix (W104)

Verified at tests/s3_integration.rs (cleanup block after `f(&store)`): a failed
cleanup `list` or `delete` is swallowed by `if let Ok(...)`, leaking objects
silently and making CI flakes hard to diagnose. Fix: `eprintln!` the cleanup
failure (test-harness-only change; the file already `eprintln!`s its skip
path).

## Part 2: Round 11 comment (5454356824) - verdicts

### r11-L1 `cargo fmt --check` fails at the tip - CONFIRMED, fix (W96)

Reproduced locally: 4 diffs, not 2 (the reviewer ran rustfmt 1.9.0-stable; the
local toolchain additionally flags two pre-existing `let cfg = parse_config_str(...)`
splits in src/config.rs:423 and src/config.rs:431 introduced by W86). The
flagged sites: src/cli.rs:1633 (W92 test chain), src/cli.rs:1702 (W93 assert),
src/config.rs:423, src/config.rs:431. The tree violates its own per-commit
gate. Fix is a bare `cargo fmt` run, landed first so every later item gates on
a clean tree.

### r11-L2 whitespace-only `[store].bucket` accepted - CONFIRMED, fix (W98)

Verified at src/config.rs:215-219: only `bucket.is_empty()` is rejected, so
`bucket = "   "` resolves and fails late at the first SDK call. The
`nonblank()` policy (W69 env region; r10-M2/W86 config region/endpoint) was
never applied to the one *required* store field. For a required field the
policy is a hard error (unlike optional region/endpoint, where blank means
unset): reject `bucket.trim().is_empty()` with a message naming the config
key, mirroring the existing "store.bucket must not be empty" error.

### r11-L3 `[store].prefix` segments validated only for emptiness - failure-mode claim REFUTED; cheap fail-fast hardening accepted (W105)

The verification split:

- **Confirmed half:** src/config.rs:238-245 rejects only empty prefix
  segments; `prefix = "a/ /b"` resolves to `"a/ /b/"` (verified by reading
  `resolve_store` + `normalize_prefix`), and `ensure_valid_key`
  (src/entity.rs:35) does reject whitespace-only and control-char segments.
- **Refuted half:** the claimed cascade - "writes objects (`a/ /b/x.md`) that
  every *subsequent* run fails to list: the whole run aborts on invalid key" -
  does not occur. `S3Store::list_prefix_objects` (src/store/s3.rs:102) lists
  under the store prefix and `strip_prefix` (src/store/s3.rs:173) removes it,
  so entity keys reaching `build_plan` are always *relative* (`x.md`), and
  `build_plan` validates only those relative keys (src/lib.rs:70-72). The
  store prefix never appears in any validated key. Proven with a compiled
  probe test (`full_key`-style concat -> `strip_prefix` ->
  `ensure_valid_key(relative)`: all green; probe run then removed). A first
  push and every later run work; the objects are oddly named but fully
  functional.
- **Accepted hardening (rescoped):** aligning prefix validation with
  `ensure_valid_key` is still worth it on its own merits: it fails fast at
  config resolution with an error naming the config value, instead of
  silently writing whitespace/control-char-segmented keys to the remote. It
  also subsumes the W58 empty-segment check with one policy. This is a small
  config-validation improvement, not a bug fix - the original severity
  justification is refuted.
