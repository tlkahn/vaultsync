## Part 1: Round 12 findings - verdicts

### M1 pull streams the full remote body before enforcing the planned size - CONFIRMED, fix (W106)

Verified: `exec_download` truth-checks on-disk size only after `store.get_to`
returns (src/exec.rs:284-296). `S3Store::get_to` streams every chunk to the
writer unbounded (src/store/s3.rs:568-576) and only checks
`written == Content-Length` after EOF. A remote object replaced between
`list` and `get` (or a misbehaving S3-compatible endpoint) with a
multi-GB body is written in full to the vault-side temp sibling before the
executor's post-stream size check fails the key. The upload side has the
symmetric bound (`open_verified` size + `put_from` reads exactly `size`, W80
5 GiB ceiling); the download side has none.

Reviewer ask accepted in the cheap form: cap in the executor (no trait
break), `a.remote` required for Download rows.

### M2 `finalize_write` re-opens the temp by path with no regular-file check - CONFIRMED, fix (W107)

Verified: src/local.rs:317 does `std::fs::File::open(tmp)` (follows symlinks)
and src/local.rs:341 renames `tmp` to the final path with no
`symlink_metadata(tmp)` regular-file check anywhere between body write and
rename. A temp path replaced with a symlink after the writer handle drops is
opened through (mtime/sync land on the target) and the *symlink inode* is
renamed onto the vault key. Every sibling path guards this class
(`open_verified` no-follow + dev/ino, destination guards, W40 `create_new`
allocation skipping pre-planted symlinks); the post-allocation window in
`finalize_write` is unguarded. The rustdoc claim "provably harmless (unique
temp name, `create_new` allocation, owner-only file)" is false twice over:
`create_new` prevents collision, not intentional replacement, and download
temps are not owner-only (L1).

### L1 download temp siblings are not `0o600` - CONFIRMED, fix (W108)

Verified: `alloc_temp_sibling_from` (src/local.rs:921-931) uses plain
`OpenOptions::new().write(true).create_new(true)` (no unix `mode`), while the
upload-temp path `create_temp_upload_file_at` (src/store/s3.rs:456-470) sets
`0o600` (W14). One policy, two implementations; the download side inherits
`0666 & umask`. Fix code-side (match the upload policy), per the reviewer's
preference over documenting the asymmetry.

### L2 object-store.md still says the reap runs on every `S3Store` construction - CONFIRMED, docs (W110)

Verified: doc/object-store.md:73-76 says "each `S3Store` construction
best-effort removes `vaultsync-upload-*` files older than 24h"; W97 gated the
reap behind `REAP_ONCE` (src/store/s3.rs:408-416, "at most once per
process"). The same paragraph is also physically inside the operations table
(between the `put_from` and `delete` rows, doc/object-store.md:71-78),
breaking the table rendering. Both fixed in the doc batch.

### L3 normative trait sketch still returns `Vec<Entity>` from `list` - CONFIRMED, docs (W110)

Verified: doc/object-store.md:21 shows
`fn list(&self, prefix: &str) -> Result<Vec<Entity>>;` directly under the
claim "Sketch matches the shipped surface in `src/store/mod.rs`"; W99 changed
the signature to `Result<Listing, Error>` (src/store/mod.rs:22-27, 55). One
block update plus a sentence on the warning channel.

### L4 reserved-namespace partition misses trailing-`/` folder form - CONFIRMED, fix (W109)

Verified: `partition_reserved_remote_keys` (src/lib.rs:145-161) takes
`e.key.rsplit('/').next()` as the final segment. For `.vaultsync-check-1/` or
`a/.name.vaultsync-tmp-1-2/`, the first rsplit yield is the empty string
after the trailing slash, so `is_reserved_vaultsync_key_name` never sees the
reserved segment and the key is kept (it then plans as `Skip(folder)` - no
transfer, but the filter's stated "final segment" policy is wrong for
folder-shaped keys, and the folder row plus its synthesized parents stay in
the plan). Reproduced by hand-simulating the split logic. Fix: strip one
trailing `/` before segment extraction (same shape as `fold_key`,
src/plan/mod.rs:394-396). Severity stays Low as filed; the fix is one line.

### N1 `list` mapping row still mentions `CommonPrefixes` - CONFIRMED, docs (W110)

Verified: doc/object-store.md:66 says "synthesize folder prefixes from
`CommonPrefixes` if delimiter `/` is used, or derive from keys"; the
implementation derives folders from keys only (no delimiter in the request,
src/store/s3.rs:113-124). One-line clarify.

### N2 "provably harmless" re-open wording - CONFIRMED, folded into W107

The rustdoc on `finalize_write` is rewritten in the same commit as the M2
fix (the check it must describe is added there), per the reviewer's ask 2.

### N3 mock does not validate keys on head/get/delete - CONFIRMED, docs (W110)

Documented trait latitude (src/store/mod.rs:44-49). One-line reminder in the
mock's module doc that `NotFound`-for-invalid-key is mock behavior per the
trait contract and S3 differs (validates first); no behavior change.

### W106 - cap download streaming at the planned size (M1)

- RED: two new tests in src/exec.rs tests.
  1. `exec_download_body_beyond_planned_size_fails_early`: a new
     `OversizedBodyStore` fixture (same delegation shape as
     `ShortBodyStore`) whose `get_to` writes 64 KiB chunks in a loop until
     the writer errors, recording `writes_attempted`, and whose inner
     `MemoryStore` seeds the key with a 5-byte entity. Seed `big.md`
     (planned size 5) and `ok.md`; build a Pull plan; execute. Assert: the
     key fails (message mentions exceeding the planned size), `ok.md` still
     downloads (isolation), `big.md` does not exist at the final path, no
     `.*.vaultsync-tmp-*` sibling remains in the vault dir, and
     `writes_attempted == 1` (the stream stopped at the cap, not after the
     full body - the core of the finding).
  2. `exec_download_requires_remote_entity`: an `Action` hand-built as
     `Download` with `remote: None` fails the key with the "download planned
     without remote entity" message (mirrors the upload guard at
     src/exec.rs:327-332). Compile-locks the `a.remote` requirement the cap
     depends on.
- GREEN: in `exec_download`, require `a.remote` (fail closed like
  `exec_upload` does for `a.local`), then wrap the temp file in a
  crate-private `CappedWriter { inner: &mut dyn Write, remaining: u64 }`
  (impl `std::io::Write`; `write`/`write_all` beyond `remaining` return
  `io::ErrorKind::WriteZero` with a message naming the key and the planned
  size). Pass the capped writer to `store.get_to`. Keep the existing
  post-stream on-disk truth-check (A-H1/B-L3) as belt-and-braces - it now
  also catches a store that ignores the writer error shape. The W66 cleanup
  tail (temp removal + created-dir removal) is unchanged and covers the new
  failure path.
- Refactor: none expected (one small struct + constructor in exec.rs).
- Docs (same commit): README known-behaviors one-liner ("a download that
  exceeds its planned size is refused mid-stream, before the extra bytes
  are written to disk"); doc/cli.md integrity paragraph gets the same fact.
- Message: `fix: refuse download bodies beyond the planned size mid-stream (PR2 W106)`

### W107 - refuse a symlinked/non-regular temp in `finalize_write` (M2)

- RED: new unix-capable test in src/local.rs tests,
  `finalize_write_refuses_symlinked_temp`: `tmp_path_for("a.md")`, write
  bytes, drop the handle, remove the temp and symlink it to an outside file
  (`TempDir` outside the vault root), call `finalize_write`. Assert: `Err`
  (message says the temp is not a regular file / is a symlink), the outside
  file's bytes are unchanged (no mtime/sync landed on it beyond what the
  filesystem does on read - assert content), the final path `a.md` does not
  exist, and the symlink temp was removed (cleanup parity with the existing
  failure arms). RED today: the call succeeds and `a.md` is the symlink.
  Companion `finalize_write_refuses_directory_temp` (tmp replaced by a dir)
  pins the non-regular arm (a rename of a dir onto a file path would
  otherwise surface as a confusing rename error or worse).
- GREEN: in `finalize_write`, before the re-open closure,
  `symlink_metadata(tmp)`: symlink or non-regular file -> remove the temp
  (a symlink `remove_file` unlinks the link itself, never the target) and
  return `Error::Other` naming the key and the observed type. Reuse the
  established message shape from `destination_freshness` /
  `delete_file_guarded` ("download temp is now a symlink: ..."). The window
  between this check and the rename inside `commit_temp` is the documented
  N3 check-then-act class - same residual the rest of the file already
  records; no new hole introduced, the previously-open window is now the
  same documented width.
- Refactor: rewrite the `finalize_write` rustdoc rationale paragraph: drop
  "provably harmless (unique temp name, `create_new` allocation, owner-only
  file)"; state instead that the re-open window is guarded by the
  regular-file check (W107) and the accidental-collision case by unique
  `create_new` names (W40), with the owner-only claim made true by W108
  (order W107 before W108: the W107 wording must not re-assert owner-only;
  W108's commit then notes the claim became true).
- Docs (same commit): none user-visible (defense-in-depth); the rustdoc
  carries the rationale.
- Message: `fix: refuse a swapped or non-regular download temp in finalize_write (PR2 W107)`
