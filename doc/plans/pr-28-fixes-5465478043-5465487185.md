### W167 - F1 GREEN: gate bytes on `ok`; shrink `total_bytes` on failure

Minimum change to flip W166 GREEN, all in `src/progress.rs` `ProgressLine::on_event`:

```rust
ProgressEvent::KeyDone { kind, key, bytes, ok } => {
    if self.pass == Some(kind) {
        self.done += 1;
        // I27-bytes (policy B, PR 28 r1 F1): failed keys still advance
        // the key count, but only successful bytes accumulate; the failed
        // key's planned bytes leave the pass total so the final frame
        // stays a clean 100% with no phantom ETA.
        if ok {
            self.bytes_done += bytes;
        } else {
            self.total_bytes = self.total_bytes.saturating_sub(bytes);
        }
        self.current_key = key;
    }
}
```

1. Update the `ProgressEvent::KeyDone` field doc (same file): `bytes` is the action's planned byte size regardless of `ok`; consumers that track transferred bytes should accumulate only on `ok` and subtract failed planned bytes from the pass total (the in-tree `ProgressLine` does exactly this).
2. Clarify one line on `execute_plan_with_progress_key_done_bytes_match_plan`'s comment in `src/exec.rs` (wire identity vs consumer policy; R28-f1-existing). No test-logic change.
3. Update the `doc/cli.md` progress bullet (living doc, same commit so code and user docs never disagree): rate/ETA count bytes of **successful** transfers only; a failed key's planned size is removed from the pass total, so a pass with failures still ends at a clean 100% with no leftover ETA.
4. Refactor under green only if the match arm wants tidying; keep the diff small.
5. Gate: new pins green; full `cargo test --locked --lib --bins` green (watch for any pre-existing test that fed `ok: false` with nonzero bytes through `ProgressLine` - adjust only if it was implicitly encoding the old policy, and call that out in the commit message).
