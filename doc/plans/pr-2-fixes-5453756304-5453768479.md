## Part 1: Round 10 comment (5453756304) - verdicts

### r10-M1 temp-sibling name overflows NAME_MAX for long leaf names - CONFIRMED, fix (W85)

`temp_sibling_candidates` (src/local.rs:775-787) embeds the full leaf name in
`.{name}.vaultsync-tmp-{pid}-{counter}`. Overhead is ~22-24 bytes, so a leaf
name longer than ~231 bytes makes every candidate exceed the 255-byte
`NAME_MAX`; `create_new` fails with `ENAMETOOLONG` (not `AlreadyExists`), so
`alloc_temp_sibling_from` returns the raw io error and the pull fails.

Reproduced live on this machine (macOS, errno 63 "File name too long"):
candidate lengths computed from leaf names of 227/228/231 bytes succeed
(250/251/254-byte temp names); 250- and 255-byte leaves fail. A 255-byte leaf
is legal on disk, pushes fine (no local temp sibling on the upload path), and
S3 allows 1024-byte keys - so vaultsync can upload a file it can never pull
back. The asymmetry claim is accurate.

### r10-M2 empty/whitespace config `store.region` / `store.endpoint` accepted - CONFIRMED, fix (W86)

src/config.rs:218-223 filters whitespace-only `AWS_REGION` on the env side
(W69), but `s.region.clone()` (line 223) and `s.endpoint.clone()` (line 241)
flow through unfiltered. `Region::new("")` / `endpoint_url("")` fail late with
an opaque SDK error. Same typo class W56/W58 closed for unknown keys/bad
prefixes; same "empty means unset" policy W69 established for env.

### r10-L1 dangling symlink invisible under `--follow-symlinks` - CONFIRMED, fix (W87)

Default mode counts every symlink (src/local.rs:948, `skipped_symlinks += 1`)
and the CLI warns (src/cli.rs:430-435). Follow mode's dangling case returns
`Ok(())` from `handle_followed_symlink` (src/local.rs:1000-1002) with no
counter and no warning, while the out-of-vault and duplicate-target cases two
branches below both warn and count. The follow-mode walk reports strictly
less about the symlink class that most often signals a moved/deleted target.

### r10-L2 upload temp buffers in `$TMPDIR` never reaped - CONFIRMED, fix (W88)

`alloc_first` (src/store/s3.rs:392-404) deliberately skips stale
`vaultsync-upload-<pid>-<n>` leftovers (correct within a run), and no
cross-run cleanup exists anywhere. A crash/SIGKILL between buffering and
`remove_file` leaks a full buffered object in the shared temp dir. Contrast
with vault-side temp siblings, which the walker counts and the CLI surfaces
(W23/W41). Real hygiene gap; the namespace pattern is fixed and known.

### r10-L3 no parent-dir fsync after rename/unlink - CONFIRMED, fix (W89)

`commit_temp` (src/local.rs:691-704) renames without fsyncing the containing
directory; `unlink_local_file` (src/local.rs:561-574) removes without fsyncing
the parent. `finalize_write`/`write_atomic` sync the temp file's bytes (W48)
but not the directory entry. Crash/power loss after a "successful" pull can
lose the dirent update. Std-only on unix (`File::open(parent).sync_all()`), so
no dependency-policy issue.

### r10-N1 `write_atomic` / `delete_file` are dead production surface - CONFIRMED, fix (W90)

Grep-verified: the only callers of `LocalFs::write_atomic` and
`LocalFs::delete_file` are unit tests inside src/local.rs. Production paths
use `tmp_path_for` + `finalize_write` (exec.rs:298-308) and
`delete_file_guarded` (exec.rs:166). No usage in tests/ (integration) either,
so `#[cfg(test)]` gating compiles. Both have already needed re-unification
with the guarded paths twice (W27, W76) - the drift class is real.

### r10 verified-not-issues - AGREED, no action

- Concurrent `block_on` on a current-thread runtime: explicitly documented as
  allowed (see r2-M1 refutation below).
- DeleteRemote head-before-delete comparing size but not mtime: rationale is
  documented (listing LastModified vs head client-metadata skew).
- Reserved-namespace partition before remote key validation: drop-before-
  validate is the desirable fail-safe order.
- Relative `vault_root` against process CWD: documented in doc/cli.md.

## Part 2: Round 2 comment (5453768479) - verdicts

This comment predates rounds 3-9. Each item re-checked against `0b5b080`.

### r2-M1 `s3_integ_list_paginates` races 16 threads against a current-thread runtime - REFUTED (false positive)

The claim that concurrent `Runtime::block_on` on a current-thread scheduler
"is not a documented contract" is wrong. Tokio 1.53.1 (the pinned version in
Cargo.lock) documents `Runtime::block_on`:

> "When the current thread scheduler is enabled `block_on` can be called
> concurrently from multiple threads. The first call will take ownership of
> the io and timer drivers. ... When the first `block_on` completes, other
> threads will be able to 'steal' the driver to allow continued execution of
> their futures."
> (tokio-1.53.1/src/runtime/runtime.rs, `Runtime::block_on` docs)

It takes `&self` precisely because concurrent entry is supported. The
reviewer's "panics on concurrent entry" worry conflates `Handle::block_on`
(whose docs warn it is error-prone on current-thread runtimes) with
`Runtime::block_on`, which is what the test uses. Round 10 independently
re-verified this and the test is green on AWS. The parallelism being partly
illusory is irrelevant: the test exercises pagination (>1000 keys), not
throughput, and concurrent puts do increase key-ingestion interleaving. No
change.

### r2-M2 `remove_empty_ancestor_dirs` linear dedup is O(n^2) - CONFIRMED, fix (W91)

Still present verbatim at src/local.rs:612 (`dirs.iter().any(|d| d == p)` per
insertion). Harmless at small scale, measurable at 50k deleted files with deep
nesting. Cheap to fix with a `HashSet<PathBuf>` seen-set alongside the ordered
Vec (ordering must be preserved for the depth-sorted bottom-up pass).

### r2-M3 no config-to-executor tolerance wiring test - CONFIRMED, fix (W92)

`cli_dispatch_uses_configured_tolerance` (src/cli.rs:1608) locks
`run_with_io`-downstream behavior, and config.rs tests lock TOML parsing of
`mtime_tolerance_ms`. But nothing locks the `run_with_settings` seam
(src/cli.rs:686, `settings.mtime_tolerance_ms` -> `run_with_io`) end to end
from a TOML file. Note: a naive `run_with_settings` test cannot observe the
tolerance, because it builds its own store internally (empty MemoryStore, or
S3Store needing credentials). The fix requires a small test seam (store
injection) - see W92.

### r2-M4 exec-report warnings not tested at CLI dispatch level - CONFIRMED, fix (W93)

src/cli.rs:487-489 prints `report.warnings` to stderr; no CLI-level test
asserts that. Executor-level coverage (`exec_reports_empty_dir_cleanup_warning`,
src/exec.rs:1440) exists, walk warnings have CLI coverage, but the dispatch
loop itself is unguarded: deleting the loop keeps the whole suite green.

### r2-M5 `s3_integ_path_style_toggle` conditional skip masks what it claims to test - CONFIRMED, fix (W94)

Still present (tests/s3_integration.rs:203-260): with
`VAULTSYNC_TEST_S3_ENDPOINT` set (MinIO/R2 - where path-style matters most)
the `path_style: false` flavor is skipped and `roundtrip >= 1` still passes on
a single flavor. Assert `roundtrip == stores.len()` and split the flavors into
clearly named tests.

### r2-L1 `PlanOpts::default()` hardcodes 1000 independently of `DEFAULT_MTIME_TOLERANCE_MS` - CONFIRMED, fix (W95)

Still present (src/plan/mod.rs:32-41 vs src/config.rs `DEFAULT_MTIME_TOLERANCE_MS`).
Two sites must change in lockstep if the product default ever moves. Use the
constant and add a coupling lock test.

### r2-L2 `finalize_write` re-opens the temp after the writer handle is dropped - DECLINED (documented rationale)

Observation accurate (src/exec.rs:298-308 -> src/local.rs:300-306), but the
reviewer himself concludes "the current approach is clearer." Passing an open
handle into `finalize_write` would couple the executor's writer lifetime to
the locality re-check/rename tail for one saved `open`+`close` per file, and
`finalize_write` also needs the path (not just the fd) for the temp-cleanup
and rename paths. The window is provably harmless (unique temp name,
create_new allocation, owner-only file). Declined; rationale recorded in the
finalize_write doc comment as part of W89's doc touch.

### r2-L3 "unused `Read` import in s3_integration.rs" - REFUTED as stated (false positive)

The import (tests/s3_integration.rs:14) is not unused: it is required by
`impl Read for Probe` (line 292). `cargo clippy --all-targets` is clean - an
actually unused import is a deny-by-default warning that would fail the build.
The suggestion to re-scope it inside one test function is purely cosmetic;
declined.

### r2-L4 `case_collision_keys` allocates full String copies - DECLINED (documented rationale)

Accurate (src/plan/mod.rs:349-384) but the reviewer notes "Not a problem at
typical scale." Rewriting to `&str` borrows ties the fold map, both side sets,
and the returned `BTreeSet` to the input lifetimes, complicating a pure
function for a constant-factor memory win at 10k+ keys only. Note W52 already
de-quadraticized `path_collision_keys`; the remaining cost here is linear with
a modest constant. Declined; revisit if profiling a large vault shows it.

### r2-L5 `check_store` size check "redundant" - REFUTED (false positive)

The claim "`ent.size != body.len()` can only fire when `buf == body` is false"
is wrong: `ent.size` is the *store-reported* size metadata of the read-back
object (src/lib.rs:187), independent of the buffer contents. A store that
returns the correct bytes but corrupt size metadata (or a mock/future store
with a bookkeeping bug) trips exactly this arm while `buf == body` holds. The
two checks cover different failure classes (payload integrity vs size
metadata). Keep; the inline comment already reads as belt-and-braces.

### r2-L6 `dispatch_plan` constructs `LocalFs` inside each match arm - ALREADY FIXED (false positive against current tree)

Fixed since the round-2 snapshot: `dispatch_plan` now builds
`LocalFs::with_follow(vault, flags.follow_symlinks)` once above its match
(src/cli.rs:474); the push/pull arms in `run_with_io` only build `PlanOpts`/
`PlanFlags`. No action.
