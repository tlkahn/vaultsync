## Scope decisions

| ID | Question | Decision |
| -- | -------- | -------- |
| R22-f1 | F1 disposition: restore sequential short-circuit vs doc-only | **Restore.** In `enrich_with_head_mtimes`, `concurrency <= 1` runs the literal pre-I20 loop (early return on the first non-NotFound head error; recoverable verbatim from `git show a2fca0a:src/store/mod.rs`); the pooled path is unchanged (no in-flight cancellation - already documented and accepted). This makes the shipped "1 = byte-for-byte pre-issue-20" claim true again instead of editing three docs to excuse the delta. The vanished-warning tail is shared by both paths (small helper) so nothing is duplicated. |
| R22-f2 | F2 disposition: hard reject vs clamp-with-warning, and the ceiling | **Hard reject above 256** (`MAX_CONCURRENCY = 256` in `src/config.rs`), same W56 loud-config shape as the existing `== 0` error (names `transfer.concurrency` and the cap). Rationale: S3 single-client throughput saturates well below 256 concurrent ops; beyond that it is OS-thread cost for zero gain, so a larger value is a config mistake, not a tuning choice - rejecting beats clamping under the project's fail-loud ethos. Config-layer only: library callers of `execute_plan`/`S3Store::new` are uncapped (pool still clamps to `items.len()`); documented as such. |
| R22-f3 | F3 disposition: document-only vs harden | **Harden cheaply + document.** Add a `dir_create_lock: Mutex<()>` to `LocalFs` held across the `tmp_path_for` create-alloc-and-cleanup tail (`with_created_dirs_cleanup(...)`) and across a new `LocalFs::cleanup_created_dirs(&self, &[PathBuf])` wrapper that exec's failure path calls instead of the free `remove_created_dirs`. In-process workers then cannot interleave a removal into another worker's create-alloc window, restoring the sequential guarantee. External actors had the same exposure pre-I20, so this is strictly no worse than the old contract. No lock nesting: `tmp_path_for` locks/releases internally; exec's wrapper locks separately afterwards. |

### W149 - F3 RED: shared-parent cleanup-race regression net

In `src/exec.rs` tests, add `exec_parallel_shared_parent_cleanup_no_spurious_failures`:

- Fresh vault per iteration; 16 keys under one new tree (`n/sub/k00.md` .. `k15.md`) seeded remotely; one poisoned `get_to` key (reuse the `ShuffleStore` poison pattern) to force a failure cleanup while siblings stream into the same fresh `n/sub`.
- Loop 200 iterations at `concurrency = 8`; assert the healthy keys NEVER fail with a `NotFound`/tmp-allocation error (only the poisoned key may appear in `failed`).
- Honest TDD note in the test comment: this is a probabilistic regression net (same ethos as the W48 overlap probes and the I20 overlap gauges), not a deterministic interleaving proof - a deterministic RED would need a test-only hook inside `tmp_path_for`, declined as production-surface pollution. ### W150 - F3 GREEN: `LocalFs` `dir_create_lock`

- `src/local.rs`: add `dir_create_lock: std::sync::Mutex<()>` (comment: I20-r1/F3 - serializes the create-alloc tail of `tmp_path_for` against created-dir cleanup so pooled workers cannot remove a shared ancestor mid-window; restores the sequential guarantee in-process).

- Verify no lock nesting (`tmp_path_for` internal cleanup runs under its own guard; exec calls the wrapper only after `tmp_path_for` returned) and no new deadlock surface (leaf lock; never held across store/IO calls beyond the fs tail it already serialized sequentially).
